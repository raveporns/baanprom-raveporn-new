# แผนงาน: Booking Feature (002-booking)

## 1. วัตถุประสงค์

ฟีเจอร์นี้ครอบคลุมกระบวนการจองงานบริการซ่อมบำรุงโดยให้ลูกค้าเลือกประเภทงาน/ที่อยู่/ช่วงเวลาและค้นหาช่างที่ว่างจริงก่อนสร้างงานยืนยันแล้ว ระบบต้องมีการล็อกช่วงเวลาแบบชั่วคราว การผูกบัตรชำระมัดจำผ่าน Payment Gateway การแจ้งข้อมูลไปยังลูกค้าและช่าง และการจัดการยกเลิกพร้อมกฎคืนมัดจำ

### 1.1 Stack ที่ทีมเลือก (team-selected)
- Frontend: React + Vite + Tailwind CSS
- Backend: FastAPI
- Database: PostgreSQL
- โครงสร้างแผนงาน: monorepo ที่มี frontend/ สำหรับ UI และ backend/ สำหรับ API + schema + migrations

## 2. ขอบเขตตาม spec

### 2.1 ฟังก์ชันหลัก
- ค้นหาช่างว่างภายใน 7 วัน
- เลือกประเภทงาน, ที่อยู่ให้บริการ, ช่าง, และช่วงเวลา
- ล็อกช่วงเวลาเพื่อป้องกันการจองซ้อนระหว่างขั้นตอนการยืนยัน
- แสดงราคา มัดจำ และเงื่อนไขยกเลิก
- ชำระมัดจำผ่าน Payment Gateway
- สร้างงานที่มีสถานะ “ยืนยันแล้ว”
- แจ้งลูกค้าและช่างภายใน 60 วินาทีหลังสร้างงาน
- คืนมัดจำตาม BR-01 เมื่อมีการยกเลิก

### 2.2 ขอบเขตที่ไม่รวม
- ระบบแนะนำช่างอัตโนมัติ
- รีวิว/ให้คะแนนช่าง
- จองโดยไม่ลงทะเบียน
- จองแทนลูกค้าโดย call center (เลื่อนไป R2)

## 3. การแมปกับความต้องการและ AC

### 3.1 ฟังก์ชันการจอง
- REQ-FN-008 → รองรับการเลือกประเภท, ที่อยู่, ช่าง, และช่วงเวลา จากช่างที่ว่างใน 7 วัน
- AC-07-01, AC-07-02 → ครอบคลุมการค้นหาและเลือกข้อมูลการจอง

### 3.2 การล็อกช่วงเวลา
- REQ-FN-041 → ล็อกช่วงเวลาชั่วคราวระหว่างขั้นที่ 3 ถึง 5
- Q-18 → ระยะล็อก = 10 นาที
- AC-07-04 → ตรวจสอบการล็อกและการปลดล็อกเมื่อหมดเวลา

### 3.3 การชำระมัดจำและการเชื่อมระบบภายนอก
- REQ-IF-001 → ชำระมัดจำผ่าน Payment Gateway ตามสัญญา (authorize แล้ว capture)
- REQ-IF-005 → กรณี gateway timeout ใช้ status inquiry ด้วย reference เดิม
- Q-19 → timeout = 30 วินาที
- AC-07-05, AC-07-06, AC-07-07 → ครอบคลุมหลักการชำระและ fallback เมื่อ timeout

### 3.4 การแจ้งเตือนและ lifecycle
- REQ-FN-012 → แจ้งลูกค้าและช่างภายใน 60 วินาทีหลังสร้างงาน
- REQ-DAT-002 → งานมีสถานะตาม MD-STM-01 และเก็บประวัติ 24 เดือน
- AC-07-03, AC-07-09 → ครอบคลุมการแจ้งและการเปิดเผยข้อมูลตามสิทธิ์

### 3.5 ความปลอดภัยและความเป็นส่วนตัว
- REQ-SEC-004 → ช่างเห็นเบอร์ลูกค้าเฉพาะ 2 ชั่วโมงก่อนนัดจนปิดงาน
- REQ-PRV-002 → เบอร์โทรลูกค้าเป็น PII ห้ามลง log
- Q-22 → ServiceAddress.geoPoint ต้องถูกจัดการเป็นข้อมูลภายในระบบและไม่ส่งออกนอกระบบ

## 4. การวิเคราะห์ลำดับงานหลัก

1. ผู้ใช้เข้าสู่หน้าจองและกรอกข้อมูลที่จำเป็น
2. ระบบตรวจสอบช่างที่ว่างภายใน 7 วัน
3. ผู้ใช้เลือกช่างและช่วงเวลา
4. ระบบล็อกช่วงเวลาชั่วคราว 10 นาที
5. ระบบแสดงราคา มัดจำ และเงื่อนไขยกเลิก
6. ผู้ใช้ยืนยันการจองและเริ่มกระบวนการชำระมัดจำ
7. หาก Payment Gateway ตอบปกติ → authorize แล้ว capture → สร้างงานยืนยันแล้ว
8. หาก timeout 30 วินาที → ทำ status inquiry ด้วย reference เดิม
9. ระบบแจ้งลูกค้าและช่างภายใน 60 วินาที
10. ระบบติดตาม lifecycle ของ Job ตาม MD-STM-01 จนสำเร็จหรือยกเลิก
11. หากมีการยกเลิกและมีเงื่อนไขคืนมัดจำ → ดำเนินคืนเงินตาม BR-01

## 5. กฎธุรกิจและข้อจำกัดที่ต้องพิจารณา

- BR-01: คืนมัดจำตาม decision table และเงื่อนไขยกเลิกที่กำหนด
- BR-02: ช่างไม่รับงานซ้อน
- BR-03: ระยะให้บริการ 15 กิโลเมตร
- REQ-CON-003: ต้องใช้ Payment Gateway รายเดิมจนถึงธันวาคม 2569
- REQ-CON-001: R1 มีเวลา 8 สัปดาห์ และทีม 4 คน
- ไม่มีข้อจำกัดเรื่องภาษา/framework; ทีมเลือกเองตาม plan.md

## 6. งานย่อยที่ต้องทำ

### 6.1 วิเคราะห์และออกแบบข้อมูล
- กำหนดคอนแทร็กต์ข้อมูลสำหรับ Job, TimeSlot, Payment, Refund, Customer, ServiceAddress
- ตรวจสอบความสัมพันธ์ของสถานะ Job, lock expiry, และประวัติสถานะ 24 เดือน
- กำหนดมาตรฐานการปกป้องข้อมูล PII

### 6.2 ออกแบบกระบวนการจอง
- สร้าง flow สำหรับการค้นหาช่างที่ว่าง
- จัดการ timeout และ retry logic ของ Payment Gateway
- ออกแบบการล็อกช่วงเวลาและการปลดล็อกเมื่อหมดเวลา

### 6.3 ออกแบบการแจ้งเตือนและ lifecycle
- สร้างข้อมูลและ event สำหรับแจ้งลูกค้าและช่าง
- ตรวจสอบสถานะและ transition ของงานตาม MD-STM-01
- จัดการเหตุการณ์ยกเลิกและคืนมัดจำ

### 6.4 ทดสอบและตรวจสอบคุณภาพ
- ทดสอบทุก path ใน UC-07
- ตรวจสอบความครอบคลุมของ BR-01 / BR-02 / BR-03
- ตรวจสอบการปกป้อง PII และสิทธิ์การเข้าถึงข้อมูล
- ตรวจประสิทธิภาพ p95 ไม่เกิน 2 วินาทีกับผู้ใช้ 500 คนพร้อมกัน

## 7. ความเสี่ยงและข้อสรุป

- การมี Q-18, Q-19, Q-22 และ Q-14 ที่ต้องใช้การตัดสินใจในช่วงเริ่มพัฒนา ต้องมีการจัดเก็บเป็นความเห็น/assumption ที่ชัดเจน
- การล็อกช่วงเวลาและการ fallback ของ Payment Gateway เป็นจุดที่มีผลต่อการจองและการคืนเงินมากที่สุด
- การจัดการ privacy สำหรับ Customer.phone และ ServiceAddress.geoPoint ต้องถูกกำหนดให้ชัดก่อนเริ่มพัฒนาเพื่อหลีกเลี่ยงการรั่วไหลของข้อมูล

## 8. ผลลัพธ์ที่คาดหวัง

งานจะเสร็จสมบูรณ์เมื่อสามารถพิสูจน์ได้ว่า:
- ลูกค้าเลือกและจองงานได้โดยไม่ชนกัน
- ระบบล็อกช่วงเวลาและปลดล็อกตามเงื่อนไขที่กำหนด
- การชำระมัดจำและ status inquiry ทำงานได้ตามสัญญา
- การแจ้งข้อมูลและ lifecycle ของงานถูกต้องตาม spec
- กฎคืนมัดจำและการปกป้องข้อมูล PII ได้รับการตรวจสอบตาม AC และ BR
